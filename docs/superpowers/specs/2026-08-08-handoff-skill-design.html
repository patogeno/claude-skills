A skill that ends a work session by flushing durable knowledge into the project's own documents, then writing one small handoff file that lets the next Claude Code session resume from a one-line prompt.

1. Problem

Multi-session work loses context at the session boundary. The naive fix — a fat "state dump" file — fails twice over: it duplicates what the plan and spec already say, so the two drift apart and the next session cannot tell which is authoritative; and it buries the handful of facts that only existed in the ended session's context.

The handoff file should therefore be defined by exclusion: it carries only what no document in the project already carries. Everything else it references by path and section.

Success criterion The next session is started with one short prompt — Read docs/handoffs/handoff-<topic>.md and continue. — and needs no further explanation from the user to take the correct next action.

The repo is distributed as a Claude Code plugin marketplace, so installation is one command and updates arrive with git pull. A single plugin holds many skills; handoff is the first.

3. Skill procedure

The skill is a six-step checklist. The invoking session creates one todo per step and completes them in order. Steps 3 and 4 are the substance; the rest bound them.

Every fact the ending session holds goes to exactly one of three destinations. Nothing is written twice.
#StepOutput
1Inventory working documentsThe plan, spec, notes, CLAUDE.md, README that actually exist in this project — with paths.
2Classify session knowledgeEach fact tagged durable / session-only / noise per §4.
3Flush durable knowledgeEdits applied to the owning documents. If a durable fact has no owning document, create the document rather than parking the fact in the handoff.
4Write the handoffdocs/handoffs/handoff-<topic>.md, rewritten in place if it exists.
5Redundancy verificationRestated lines deleted and replaced by references; empty sections removed.
6Emit the resume promptOne line the user copies into the next session.

Topic and path resolution

The topic is derived, in order of preference, from: an argument the user passed to the skill, the plan document being executed, the branch name, or the dominant subject of the session. Handoffs live in docs/handoffs/; if the project has no docs/ directory the skill creates it rather than falling back to a cluttered project root. One living file per topic — successive sessions rewrite it, and git history preserves prior versions.

The rule that keeps the handoff small A durable fact with no home does not become a handoff bullet. It becomes a document — a new plan file, a new spec section, a new CLAUDE.md line. The handoff is not a landfill for homeless knowledge.

5. Handoff file contract

Markdown, because the next session reads it as an instruction. Every section is droppable: an empty section is deleted, never filled with a placeholder.

# Handoff: <topic>

**Goal:** <the outcome that ends this multi-session effort>
**Status:** <where the work actually stands, 1–2 sentences>

## Start here
1. Read <path> §<section> — <why>
2. <first concrete action>

## Orientation
| Document | Holds | Read when |

## Not written anywhere else
<facts that exist in no document — delete ruthlessly>

## Do not
- <what wastes the next session's time or breaks something>

## Open questions for the user

## Environment
<only if non-obvious>

Size limit: under 80 lines. Exceeding it is a signal that durable knowledge is being duplicated instead of flushed, not a signal to raise the limit.

6. Verification & exit

Step 5 asks two questions of the drafted file:

  1. Per line: is this already stated in a working document? If yes, delete it and, if the next session needs to know it exists, replace it with a path-and-section reference.
  2. Of "Start here": could a session with zero memory of this conversation act on step 1 immediately? If not, make it concrete.

Step 6 prints the resume prompt as a copyable line and nothing else:

Read docs/handoffs/handoff-<topic>.md and continue.

7. Public-repo constraints

The repository is public and its skills must work in anyone's project. These are repo conventions, stated in the README and applied to every skill added later.

ConstraintApplies to
No absolute paths, drive letters, or home directoriesevery SKILL.md
No usernames, company names, or project namesevery file in the repo
No secrets, tokens, hostnames, or internal URLsevery file in the repo
No assumption that a given directory exists — state the fallbackskill procedures that write files
No OS-specific shell syntax in skill instructionsevery SKILL.md

The generated handoff file lives in the consuming project, not here, so its contents are that project's concern. The skill nonetheless warns against copying secrets or credentials into it, since handoffs are often committed.

8. Out of scope

  • A receiving-side skill. The handoff file is self-directing; no second skill is needed to consume it.
  • Automatic invocation at session end. The user runs /handoff deliberately.
  • Multi-topic handoffs. One topic per file; run the skill twice for two parallel efforts.
  • Archiving or pruning old handoffs. Rewriting one living file makes git the history.
  • Additional skills. This spec covers the scaffold and handoff only.
